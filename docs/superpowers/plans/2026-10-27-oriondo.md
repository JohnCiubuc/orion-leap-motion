# OrionDo Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A finger-driven radial menu: a hand pose opens an animated pie on the focused monitor, the index fingertip steers a marker, and pulling past the activation distance fires the item's action.

**Architecture:** `OrionDo` is a self-contained `Gesture` holding the state machine and the item tree. The engine forwards its events to the overlay process and runs a fired item's action through the existing `Executor`. The overlay owns all easing: a pure-Python `MenuAnim` computes per-frame view values (unit-testable) and a thin GTK window draws them with cairo.

**Tech Stack:** Python 3.12, numpy, pytest; GTK4 + gtk4-layer-shell + cairo in the overlay child process; evdev uinput via the existing `input.keys` action.

**Spec:** `docs/superpowers/specs/2026-10-27-oriondo-design.md`. One delta from it: the overlay side is split in two files, `menu_anim.py` (pure animation math) and `overlay_menu.py` (GTK drawing), so the animation can be tested without GTK.

All paths below are relative to `application/`. Run tests with `cd application && python -m pytest tests/test_core.py -q`.

## Global Constraints

- Defaults: `deadzone` 8 mm, `pull` 35 mm, `lost` 1.5 s, `cooldown` 0.6 s, trigger pose `peace`. Slice-border hysteresis 4°.
- Items are plain data `{label, action, args}`, listed clockwise from the top; list order is position; N items are 360/N° apart. No per-item angle, no item ids.
- Items live in config under `[gestures.oriondo]`; the gesture re-reads them on every rebuild (no caching outside config) so a future UI edit applies live.
- Marker uses the index fingertip x/y (Leap +y up); depth ignored. The marker sent to the overlay is divided by `pull` (1.0 = activation ring).
- Overlay: layer-shell `OVERLAY` layer, namespace `orion-menu`, empty input region (click-through), full focused monitor, cairo renderer, redraw ≤ 60 Hz and only while visible; engine→overlay `update` messages throttled to ≥ 16 ms apart.
- Animation: open bloom with 25 ms stagger and overshoot; close is the reverse; hover lift; pull stretch + arc; marker exponential smoothing with trail; fire flash then collapse.
- Match the surrounding code: docstring-light, one-line comments for the why, no new dependencies.
- OrionDo must not open while paused, in an exclusive mode, or without a running overlay.

## Review Focus

1. **Brief hand loss, then the hand returns** inside `lost`: the menu stays open and the marker keeps its origin (no re-origin, no close). *(Task 1 test)*
2. **A second hand makes the trigger pose while the menu is open**: ignored; the opener's hand keeps control. *(Task 1 test)*
3. **0 and 1 items**: 0 never opens (no exception); 1 item means every direction selects it. *(Task 1 tests)*
4. **A fast flick** (marker jumps from center past `pull` in one frame, e.g. a dropped frame): fires the item in that direction rather than nothing. *(Task 1 test)*
5. **Config reload or overlay failure while the menu is open**: reload closes the open menu on the overlay; an overlay that cannot show leaves the gesture unable to open. *(Task 2 tests)*

**Interfaces:**
- Produces `class OrionDo(Gesture)`, `name = "oriondo"`, `family = "oriondo"`, with:
  - `params`: `trigger` `("peace", <tuple of registered pose names>)`, `deadzone` `(8, 2, 40)`, `pull` `(35, 15, 120)`, `lost` `(1.5, 0.2, 5.0)`, `cooldown` `(0.6, 0.0, 3.0)`, `tap_trigger` `(5, 1, 30)`, `tap_still` `(60, 10, 200)`.
  - `__init__(self, overrides=None)`: reads `items` (list of dicts) straight from `overrides`, since the base class drops undeclared keys. `reset()` is overridden to keep `items`. Attribute `self.items: list[dict]`.

    - `fire`, value `{"index": int, "item": dict}`, immediately followed by `end` with value `"fired"`
    - `end`, value `"fired" | "tap" | "lost"`

- [ ] **Step 3: Implement `OrionDo` in `orion/gestures/oriondo.py`.** Structure: `update(frame)` first feeds the wrapped trigger pose (`REGISTRY[trigger]()` built in `__init__`; skip if the name is unknown) and notes its `begin` events; an open menu is handled before a new open is considered. Rules:
  - open on the pose's `begin` only if no menu is open, `frame.t ≥ cooldown_until`, `items` non-empty, and `allow()`; origin = that hand's `h["index"].tip[:2]`;
  - while open, track the opener's side only; marker `m = tip[:2] − origin`; `r = |m|`; sector angle `θ = atan2(m.x, m.y)` in degrees clockwise from the top, nearest item `round(θ / (360/N)) % N`, kept while within `180/N + 4°` of the current hover's centre; `hover = None` while `r < deadzone`;
  - fire when `r ≥ pull` using the freshly computed sector (not the previous hover); progress `clamp((r − deadzone) / (pull − deadzone))`;
  - tap = a `FingerMotion` (one per open menu, fed `np.array([f.tip − h.palm for f in h.fingers])`, `|h.velocity|`, `tap_trigger`, `tap_still`); it closes the menu only while `r < deadzone`;
  - hand missing for more than `lost` seconds closes with `"lost"`; every close sets `cooldown_until = t + cooldown`.

  Register the module in `load_builtins` so `trigger`'s choices (pose names, taken from `REGISTRY` after `poses` is imported) exist.

### Task 3: Menu animation model (pure)

**Files:**
- Create: `orion/menu_anim.py` (no imports from the rest of the package, so the GTK overlay script can import it by bare name)
- Test: `tests/test_core.py`

**Interfaces:**
- Produces:
  - `@dataclass SliceView(scale, alpha, lift, stretch, glow, flash)`, all floats 0…~1.1 (scale may overshoot above 1).
  - `@dataclass MenuView(visible: bool, slices: list[SliceView], marker: tuple[float, float], arc: float, hover: int | None)`
  - `class MenuAnim` with `open(labels, now)`, `update(x, y, hover, pull, now)`, `fire(index, now)`, `close(now)`, `step(now) -> MenuView`, and `labels: list[str]`. `now` is monotonic seconds supplied by the caller. Marker coordinates are in units of `pull` (as received).
  - Easing helpers `ease_out_cubic(t)`, `ease_out_back(t)` clamped to 0…1 input.
- Timings (constants at the top of the file): open 0.28 s with 0.025 s stagger per slice, close 0.18 s, hover ease 0.12 s, fire flash 0.14 s then collapse 0.2 s, marker follow time constant 0.04 s.

- [ ] **Step 1: Write failing tests:**

  - `test_anim_hover_lifts_only_the_hovered_slice`: after `update(0, 0.3, 0, 0.4, t)` and settling 0.3 s, slice 0 has `lift > 0` and others 0; moving hover to 2 returns slice 0 to 0 and raises slice 2.
  - `test_anim_pull_stretches_and_fills_arc`: `pull` 0.8 → `stretch` of the hovered slice and `arc` both ≈ 0.8 after settling; `hover=None` → `arc == 0`.
  - `test_anim_marker_smooths_toward_target`: `update(1, 0, …)` then `step` at +0.01 s is strictly between 0 and 1 and at +0.5 s is within 0.01 of 1.
  - `test_anim_fire_flashes_then_collapses_and_hides`: after `fire(1, t)`, `flash` of slice 1 peaks > 0.8 within 0.14 s; at `t + 0.5` `visible is False`.
  - `test_anim_close_reverses_and_hides`: `close(t)` → scales fall to 0 and `visible is False` after 0.2 s; `open` again after hide restarts from scale 0.
  - `test_anim_reopen_during_close_restarts`: `open` while closing resets to the bloom, no stale `visible=False`.
